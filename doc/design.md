原项目 [ast-hook-for-js-RE](https://github.com/JSREI/ast-hook-for-js-RE) 使用中间服务器拦截并修改请求、使用 `Babel` 处理 JS 代码。

chrome 插件也可以拦截并修改请求，但是使用 `Babel` 就显得慢了，造成网页加载缓慢，所以使用 [swc](https://github.com/swc-project/swc) 来处理 JS 代码。

# swc wasm web

使用 [@swc/wasm-web](https://swc.rs/docs/usage/wasm) 可以在网页中使用 swc 来处理 JS 代码 —— 但它不能加载 `swc wasm` 插件！

# native messaging

chrome 插件可以和本地程序通信，使用 [swc_core - Docs.rs](https://docs.rs/crate/swc_core/latest) 开发处理 JS 的程序，让插件将要处理的 JS 代码发过来就行。

但它有以下缺点:

1.  本地程序每一次发送的消息最大只能是 `1 MiB`，如果是大文件，需要分片发送
2.  为了**保证插件每一次发送的消息都能拿到对应的处理结果（可能会异步发送消息）**，需要每次都启动独立的程序来处理
3.  在处理动态生成的 JS 代码时，只能从网页中将数据传回插件，然后再由插件发送！这整个过程是异步的！—— **这是最大的缺点**！

# HTTP Server

综上所述，最后只能选择搭建 HTTP 服务器来处理了：

1.  插件拦截响应，将 js code 发送到服务器
2.  服务器处理之后，返回新的 js code 给插件，让其完成响应的重写
3.  动态生成 js code 时，使用同步请求，将其发送到服务器
4.  服务器处理之后返回新的 js code

经过测试，该方案可行，但是速度不太行，和 `native messaging` 方案相比较差距太大了！难道，还是要使用中间服务器吗？！

# 组合

尝试使用 `HTTP Server + native messaging`，且 `native messaging` 开始时，插件和它建立通道（只打开一个通道）。

- 经过测试，当本地程序发送的数据太大时会直接退出，需要分片发送 —— 因为它确实比 HTTP Server 快！
- 对于动态生成的 js code，使用 `HTTP Server` 处理

也就是说：

- 默认情况下，本地程序以 `native messaging` 方式运行
- 插件可以发送一个 `native messaging` 消息，让本地程序切换到 `HTTP Server` 方式运行

# 放弃 HTTP Server

因为网站有大量 `eval` 等动态生成的 js 代码，如果全都使用 http server 去处理，这不是对自己发起服务器攻击？！而且效率大大折扣！

# JS 操作 AST

对于如何处理动态生成的 js 代码，和 AI 激情交流之后，有以下方案：

1.  使用 `@swc/wasm-web` 生成 AST，然后使用 JS 操作 AST，生成最终的 JS 代码
2.  使用一些轻量的、JS 实现的 AST 操作库来专门处理

考虑到性能（要快），使用第一个方案 —— 饶了一大圈，**还是回到了开头，难道这就是宿命的牢笼、命运的轮回、无法逃避的命中注定**，库库库 ヾ(≧▽≦\*)o，事到如今，自然是先看动漫再继续！

# ALL STAR

再和 AI 激烈交流思想之后，结合上面各种方案的优缺点，组合多方案：

-   默认情况下使用 `native messaging` 处理请求的 html、js
-   在处理动态生成的 js 时
    -   如果 js 代码较少，使用 JS 操作 AST 完成处理
    -   如果 js 代码较多，则使用 http server 完成处理
    -   当 js 代码达到一定长度就认为它“较多”

经过测试，效率明显提升！现在的唯一缺点是：怎么确保 `swc wasm` 先初始化完成，然后再执行网站代码 —— 初始化 wasm 的过程是异步的！
